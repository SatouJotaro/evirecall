# 讨论与决策记录

记录日期：2026-10-27。依据：团队发起人提供的小组讨论摘要与后续方案交流。本文为决策脉络整理，不是逐字聊天记录；不把助手提出的候选项当作团队已批准事项。

## 讨论如何收敛

1. **从开放选题转向 Agent 可靠性。** 2026-10-23 的小组讨论倾向 Agent 相关方向，关注多 Agent 稳定性、长任务退化、记忆与证据，也提出资源调度和 benchmark 的可能价值。
2. **复用现有系统和数据。** 后续讨论希望接入或改造 memory，优先复用已有多 Agent 系统与评测集，把工作集中在可解释的改进及验证。
3. **兼顾算法与工程深度。** 团队存在偏算法与偏后端 / AI Infra 的成员，因此需要同一项目内可区分的方法、系统和实验贡献。就业价值是内部选题考虑；研究结论仍由实验支持。
4. **曾比较不同底座。** Smurfs 与 Deep Agents 都被讨论过。Deep Agents 曾作为工程候选；最新决定明确选择教师团队的 Smurfs，取代此前的底座建议。
5. **评测的两个层次。** 建议以 LongMemEval 检查记忆能力，以 MemoryArena 检查记忆对后续行动的价值。“两个 benchmark”与“训练 / 开发 / 测试划分”不是同一件事。
6. **形成仓库与项目名称。** 发起人创建 SatouJotaro/evirecall 仓库，沿用 EviRecall 作为展示名称，并承担方案统筹和 proposal 编写。
7. **最新范围。** Smurfs 已确定；进一步考察 TierMem 中 Jev 轻量应用的融合方式。总体计划尚未确定，因此先交付带验证门槛的 v0.1。

## 已确定

- 三人合作，仓库为 https://github.com/SatouJotaro/evirecall 。
- 以 Smurfs 为多 Agent 底座，研究 memory、长任务证据与错误。
- proposal 包含选型理由、文献来源、评测设计和拟议分工。
- 发起人牵头收敛方案和撰写 proposal。

## 当前建议，尚待团队冻结

- Jev TierMem 作为首选待验证记忆组件，采用 Python 适配。
- LongMemEval_S 清洗版加 MemoryArena 的一个子任务。
- 先做无需参数训练的记忆策略，以“显式约束更新后的依赖失效处理”为候选改进。
- 将检索预算、并发和超时作为评测维度；不同时建设通用调度平台。
- 分工按 A（统筹与评测）、B（记忆方法）、C（系统与 Infra）占位，尚未对应另外两名成员姓名。

## 可行性阶段需要回答

- Jev 是否有可用且可负担的服务？返回哪些可计费用量？服务故障如何标记？
- Smurfs 的工具循环能否接入 MemoryArena 并保持相同环境反馈和终止条件？
- 任务是否确实需要跨角色 / 跨会话记忆？若无记忆也能完成，如何解释该子任务的评测价值？
- 哪一种明确更新关系可被可靠识别？与已有记忆治理工作的区别是什么？
- 选择哪个任务模型、judge 模型、测试规模、预算上限和重复次数？
- proposal 的最新课程模板、提交语言和日期是什么？
