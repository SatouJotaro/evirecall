\textbf{Project summary.} We propose to extend Smurfs with evidence-aware shared memory and investigate whether checking recalled evidence prevents stale information from affecting later decisions. Our contribution will combine one memory intervention, controlled evidence/error experiments, and a reproducible benchmark harness. This is a research plan; no performance improvements are claimed.

\section{Motivation and research questions}
Multi-agent tasks depend on information passed between planning, execution, answering, and verification roles. Compressed memory can omit a decisive constraint. Even a correctly cited summary can become outdated after the user or environment supplies new evidence. Reusing that summary may propagate an error across roles and subsequent tasks.

For example, a travel-planning agent may retain a plan after a user reduces the budget. Later roles might reuse that plan and verify only its final wording, without revisiting the changed constraint. This is an illustrative scenario, not an experimental observation.

\begin{itemize}
\item \textbf{RQ1 - Memory utility:} Does tiered memory improve recall and subsequent task completion over recent history and ordinary retrieval?
\item \textbf{RQ2 - Evidence and recovery:} Does checking evidence validity reduce stale-information reuse across roles and improve recovery after an update?
\item \textbf{RQ3 - Resource trade-offs:} How do evidence budgets and task concurrency affect quality, cost, and completion time?
\end{itemize}
\textbf{Current choice.} Use Smurfs as the fixed multi-agent backbone; pilot Jev TierMem as the first memory backend; evaluate general memory with LongMemEval and stale-memory behavior with STALE. Add a small MemoryArena action study if its environment passes the feasibility pilot. MAST informs failure annotation. No parameter training is required in the first version.

\textbf{Expected outputs.} A reusable memory adapter and intervention; source-linked task traces and error analysis; reproducible comparisons and resource measurements. The following sections document the alternatives considered and how this scope was chosen.

\section{What we will build}
\textbf{A. Memory integration and one intervention.} Connect Smurfs to a replaceable adapter with immutable source IDs and typed observations. Before reusing a summary affected by an explicit, authoritative update, check its validity, mark dependent conclusions for review, and recover raw evidence within budget. Preserve old records; ambiguous changes remain uncertain. Provenance and invalidation are existing ideas; our contribution is their controlled study at Smurfs role handoffs. STALE tests generalization to implicit conflicts without gold update labels.

\textbf{B. Evidence and error experiments.} Paired update/no-update variants form a separate stress suite, not official MemoryArena scores. Track stale-evidence reads, reuse across roles, and recovery. Use STALE and the travel pilot, with evidence-support labels and a MAST-informed error rubric.

\textbf{C. A shared benchmark harness.} Run matched conditions, isolate stores, collect traces and costs, and recompute metrics from saved outputs. Add a limited budget/concurrency sweep.

The proposed adapter uses {\small\texttt{observe()}}, {\small\texttt{add\_summary()}}, and {\small\texttt{retrieve()}}; write-back via {\small\texttt{promote()}} is explicit. Smurfs generates answers and verifies them against the returned evidence.

\section{Experimental design}
\subsection{Comparisons and ablations}
\begin{itemize}
\item \textbf{Memory QA:} recent history, BM25 over identical raw chunks, unmodified Jev, and Jev plus our intervention. Fix the answer model; disclose additional models.
\item \textbf{Closest method:} CUP-Mem on a matched STALE subset, subject to pilot feasibility. If unavailable, disclose the missing comparison and narrow claims.
\item \textbf{Actions:} Smurfs without persistent memory, with Jev, and with our intervention; hold tools, observations, models, and limits constant.
\item \textbf{Ablations:} disable validity filtering or raw-evidence recovery separately. Claims about multi-agent benefits require a budget-matched single-agent control.
\end{itemize}
\subsection{Data isolation and experimental scale}
Split by complete history, scenario, or task group. Gold answers, evidence-location labels, conflict explanations, and scoring state remain evaluator-only. Retain intended multi-session history but isolate stores across groups and conditions; fix query-level write-back policy. LongMemEval S, M, and oracle are context settings, not splits.

Pilot 10 development units per primary dataset and 3 travel groups. Provisionally target 100 held-out LongMemEval questions, 100 STALE scenarios, and 20 travel groups after cost estimation. Freeze IDs, prompts, models, judge, and budgets. Report coverage and counts; aim for three repetitions where affordable, with uncertainty grouped by history/scenario/task.

\subsection{Quality, evidence, and recovery metrics}
Use official scorers, category-level results, and human checks. Distinguish citation existence, evidence recall, and semantic support. For update cases:

\begin{itemize}
\item \textbf{Stale-use rate:} stale-dependent decisions / eligible post-update decisions.
\item \textbf{Cross-role propagation rate:} update episodes with stale evidence reused by another role / update episodes.
\item \textbf{Recovery rate:} corrected, successful episodes / update episodes.
\end{itemize}
Report denominators, failures, reviewer disagreement, and representative successful and failed traces.

\subsection{Resource benchmark}
Vary evidence budget and concurrency (1, 2, 4) separately on a fixed subset, holding tools and retry policy constant.

Count all role, summary, retrieval, Jev, and retry calls, including failed runs. Separate ingestion, execution, and evaluation-judge costs. Report tokens, requests, throughput, and latency including queue time; unknown usage is not zero. Label injected delays as synthetic. API results do not establish GPU utilization or hardware-scheduling performance.
