01第一版主要解决哪一种记忆更新？

例如用户把预算从 5000 元改为 3000 元，旧行程仍可能被其他 Agent 引用。我们需要一个能实现、能观察，也能公平对照的干预。

03开发和主实验如何统一模型？

主比较需要固定任务／回答模型。Jev 的判断服务和评分模型单独记录，避免把更强模型带来的变化当成 memory 的效果。

建议起点：优先使用三人都能复现的同一 API 配置；先测工具调用、上下文限制、用量和失败情况，再冻结具体版本。

03 / DISCUSSION

怎样判断错误

把同一条执行轨迹放在一起看，比只讨论指标名称更容易达成一致。

Bijun 起草规则，另外两人共同核对

讨论案例：预算已经下调，Planner 仍沿用旧预算，Executor 又据此生成方案；Verifier 发现问题后要求重做，最终方案满足新预算且完成任务。这个案例可以同时出现“错误传播”和“最终恢复成功”。
05如何记录旧记忆使用和跨角色错误传播？

引用过旧记录，不一定代表决策依赖它；一个来源 ID 存在，也不意味着它支持当前决定。需要区分检索、使用和传播。

建议起点：分别记录更新后的旧证据依赖决策、跨角色复用，以及最终结果。预先约定哪些决策有资格进入分母。

06什么情况算恢复成功？

“发现旧记忆”“修正约束”和“完成正确任务”是不同阶段。统一定义后，程序评分和人工分析才可比较。

建议起点：把纠正后的任务成功作为严格恢复标准，同时单独记录发现错误、修正证据和部分恢复。

07哪些 memory 对照是核心结果的必要条件？

现有 proposal 计划 recent history、BM25、原始 Jev、Jev＋干预；CUP-Mem 是 STALE 上优先尝试的相近方法。最终比较须取决于接入证据与预算。

建议起点：保留简单基线、未改动后端和改进版本，帮助区分检索收益与新机制收益；CUP-Mem 先做可行性检查。

08数据与实验规模如何推进？

LongMemEval 与 STALE 是两套评测资源，各自需要开发／测试划分。按完整历史、场景或任务组分割，并检查共享来源。MemoryArena 行动环境仍需试跑。

建议起点：沿用 proposal 的小样本起点：每套主要数据 10 个开发单元、3 个 travel 组；这些是试跑目标，最终规模由成本和环境可用性决定。

09资源 benchmark 的范围限定在哪里？

当前方案研究证据预算和 API 任务并发。API 延迟、吞吐和限流结果不能直接解释为 GPU 调度效果。

建议起点：在固定子集上分别改变证据预算与并发 1／2／4，保持工具和重试策略一致，并统计排队、失败与重试成本。
